# Develop with DalamudMCP

Use the connected DalamudMCP server to answer runtime questions and validate a plugin against the game. Source editing and builds still use normal development tools. Follow the user's game-interaction restrictions and existing authorization; installing this skill does not authorize new actions, commits or pushes.

## Keep an installed copy current

At task start, use `get_agent_guidance` when available; the running server supplies the matching skill revision without GitHub access. Follow its bounded client-side synchronization instructions when local execution and user/client policy permit. Pass the managed state's revision if present; request `includeBundle=true` for installation or an update. Verify the returned updater script against the manifest before executing it. The [sync helper](scripts/sync_skill.py) accepts the saved tool JSON via `--payload`, the actual selected skill directory via `--target`, and `--apply`. Pristine known older copies and unchanged managed copies update without another confirmation unless client policy requires it. Read the updated `SKILL.md` before continuing; refresh client discovery if needed.

Do not overwrite custom edits, unknown/newer revisions, symlinked copies, this repository's canonical source, or project/client instructions. On conflict or unavailable local execution, read current `SKILL.md` with `get_agent_guidance(file="SKILL.md")` for this session and report the gap once. Avoid duplicate project/user installations. These instructions do not grant new filesystem permissions or bypass a user's update policy.

## Orient and choose tools

Call `get_client_state`, then `get_local_player` before live work. If disconnected or logged out, continue independent source/build work and report what cannot be verified. Do not substitute assumed client state.

Discover the relevant tools and read their actual schemas. Namespace prefixes depend on the agent client. When using raw MCP, follow every `nextCursor` from `tools/list`; a first page is not the full catalog. Mutating tools are hidden/refused when `AllowMutatingTools` is off, so absence alone does not prove a missing capability. Do not bypass that gate. From 1.0.0.44 the server advertises `tools.listChanged=true`. Clients should receive `notifications/tools/list_changed`, invalidate cached discovery and re-read all pages. HTTP needs a GET /mcp event stream; stdio needs the updated bridge. Notifications do not force a host to refresh its model tool inventory. After a server restart HTTP sessions must reinitialize; the new bridge can re-handshake and forward an invalidation. Do not assume an old conversation has loaded new schemas without refreshed discovery.

For repository and installed-plugin changes, discover exact targets with `list_plugin_repositories`, `list_available_plugins` and `plugin_list` first. Use `add_plugin_repository`, `remove_plugin_repository`, `set_plugin_repository_enabled`, `refresh_plugin_repositories`, `install_plugin` and `uninstall_plugin` within the user's scope. Installation requires the observed source URL and version. Poll `get_plugin_operation` to a terminal state before repeating a change; an in-flight Dalamud task cannot be cancelled by disconnecting or closing the mutation gate. Check `refreshSucceeded`, actual installed/load state and deferred deletion flags. See [plugin installer tools](https://github.com/NiGuangOwO/DalamudMCP/blob/main/docs/plugin-installer.md).

Read [tool-selection.md](references/tool-selection.md) when choosing observation, UI, event or plugin-loading tools. Prefer typed state and node observations to raw memory when they answer the question. For native UI text, use `read_addon_text`; use `list_addon_elements` or `get_addon_strings` for narrower follow-up reads. Use `capture` for visual pixels and cached screenshot crops when structured data cannot answer the question. Prefer native text/geometry for ordinary labels and controls. Screenshots are captured through the SDK, independently of the DalamudCN MCP service. Inspect the current addon and component scope before choosing a node or event.

Operate native FFXIV UI only through a verified game callback, registered native event, or supported native UI API. Prefer an existing typed adapter. For a known contract, use `fire_addon_callback` with the exact live addon name and observed ID, and start with `dryRun=true`. If an action has no supported adapter or known contract, discover the real callback and add a bounded adapter before proceeding. Do not substitute virtual keys, window messages, coordinate clicks, desktop automation, or input simulation through generic runtime tools. Use dedicated movement and action tools for gameplay.

For live game tests, read [gameplay-workflows.md](references/gameplay-workflows.md). Use `move_and_wait` for verified travel (prefer mounted flight outdoors), `interact_with_npc` for known NPC dialogues, and `click_addon_button_and_wait` for verified native arrival or UI. For an authorized opener, `execute_action` can wait briefly on the exact target. Use `combat_recording_wait` with the exact encounter and an optional game outcome guard.

## Develop and verify

Gather the smallest observation that distinguishes the behavior being investigated. Implement the plugin change, build against the developer's installed Dalamud SDK, and run checks appropriate to that change.

For a local development plugin, discover `list_dev_plugins` and inspect `get_dev_plugin_state` with the exact absolute DLL path before building. The list includes explicit missing DLL registrations; other location kinds are counted, not scanned. Duplicate internal names can have different paths. If `autoReload=true`, build and call read-only `wait_for_dev_plugin`, optionally guarding with the finished DLL's `expectedBuildMvid`; do not call `load_dev_plugin` or change the watcher. Require `status=ready`, `buildVerified=true` and the matching `buildMvid` before test commands. A loaded name or `buildMatches=true` snapshot alone does not establish stable readiness. The wait pins the build at request start, requires 750ms of stable loaded state, and reports timeout without loading anything. If registration/loading or an explicitly authorized watcher change is needed, use `load_dev_plugin` with the absolute DLL path and sibling manifest. Omitted `autoReload` preserves existing settings; only new registrations default to true. A disabled watcher and obsolete loaded build need an authorized lifecycle action, not repeated waits. Loading the MCP host through its own loader is refused. For MCP host changes, use the existing reload mechanism, reconnect after reload and compare `/health.buildMvid` with the tested DLL; a pending request cannot survive host unload.

When loading a local plugin, check `plugin_list` for the exact same `internalName` with `isDev=false`. If that repository-installed plugin is enabled, disable it first with `disable_repository_plugin` using its observed `internalName` and `expectedVersion`. Poll `get_plugin_operation` to terminal success, require `stateVerified=true` and `enabled=false`, then re-read `plugin_list` to confirm that online instance is unloaded. Only then load the local DLL and verify its MVID. This ordered switch is authorized when the user asks to use the local version; do not uninstall the online copy or delete its configuration. Keep it disabled while the local version is in use. A successful disable dispatch is not evidence of unloading; legacy `manage_plugin` command dispatch is insufficient for this switch. If the target is ambiguous or transitioning, or disable verification fails, resolve it through runtime discovery and do not load both. The loader independently refuses an enabled/wanted online instance, while allowing a disabled and unloaded same-name online installation to remain installed.

Use `set_dev_plugin_settings` for explicitly requested `startOnBoot`, `autoReload` or `notifyForErrors` changes without loading the plugin. `unload_dev_plugin` preserves registration and watcher settings; later file changes may reload it. `remove_dev_plugin` unloads/disposes the current instance and removes one exact explicit DLL location, including missing DLL registrations. It preserves binaries, manifests and plugin configuration, never removes folder locations, and cannot prevent rediscovery from Dalamud's default developer folder. These mutations refuse the MCP host and lifecycle transitions. A timeout does not cancel a started Dalamud task; inspect the resulting list/state before retrying. Developer lifecycle mutations stay serialized until that task ends. See [developer plugin management](https://github.com/NiGuangOwO/DalamudMCP/blob/main/docs/dev-plugin-management.md).

If an explicit reload of an already loaded developer plugin is warranted (for example, its unchanged loader does not notice rebuilt child assemblies), use `reload_dev_plugin` by exact path. It verifies a new loader assembly instance and the finished DLL MVID. Verify child builds separately through that plugin's diagnostics. Inspect before retrying a timeout; Dalamud may still be reloading.

After an authorized action, read the resulting state. `fired`, `triggered`, command dispatch, or a callback return alone do not prove that the desired transition, reward, load or unload happened. Distinguish unavailable/no-op branches from actual action success. Restore temporary probes, subscriptions and configuration introduced by the test as appropriate.

## Improve a missing capability

If the full catalog cannot answer a necessary question and MCP development is in scope, add a reusable tool before relying on a one-off workaround in the plugin. Define bounded inputs/output, framework-thread access, cancellation/cleanup and the appropriate mutation gate. Validate against the installed SDK, test the actual failure mode offline, verify the running build, then perform a limited live check and resume the original plugin task. Report any remaining gap rather than claiming it was verified.

For native memory, signatures, hooks, or a client crash, read [native-debugging.md](references/native-debugging.md) before experimenting. Do not repeat a crash-inducing live call to discover whether a speculative fix works.

Report the change, tested build, observed result and material untested scenarios. Keep raw character identity, chat and full memory dumps out of shared reports unless the task requires them.

## Independent runtime exploration

Use `service_list` and `object_access` to discover already-constructed services and loaded managed types/members; `Describe` does not invoke getters. Read/Query can invoke getters, so all `object_access` actions require the mutation gate. Use exact discovered member ids, bounded projections and explicit object `Release`. `ffcs_index` discovers native layouts, symbols and supported wrappers; `ffcs_call` only supports resolved SDK MemberFunction/StaticAddress scalar/pointer signatures. Instance calls use the live this address, not a boxed copy. Borrowed byte-pointer text expires after the call and must never be retained by the callee. Virtual, by-reference and structure-by-value calls are refused.

`mem_read`/`mem_write` use guarded process-memory operations; mapped memory is not proof of object identity or lifetime. `mem_scan` requires an explicit range of at most 16 MiB; incomplete scans must not prove absence. `observe` supports finite Memwatch, resolved native Hook, Managedhook and Hostevent observations. Generic native hooks reject bool/unverified ABIs. Read non-draining `evidence` using nextCursor and gap, then remove observations. All observers are removed on mutation-gate closure/unload; frame-stop cleanup waits for framework ticks. Managedhook detects a compatible host-provided 0Harmony backend on demand; if absent, it returns unavailable without preventing plugin loading or other observations. Hooks change execution timing and managed inlining can hide calls. Do not install native hooks merely to discover an ABI; use the native-debugging reference and isolated verification first.

`input` playback targets Dear ImGui plugin UI only and uses the owned virtual-pointer scheduler. Discover the plugin command/IPC first when it provides the action; otherwise guard ImGui input with the observed window and control. A capture reference maps image pixels to the viewport; moved/resized or older-than-15-second references are refused. Human input preempts batches. Completion proves dispatch only: inspect actual resulting state before another non-idempotent action. No tool in this group connects to another MCP endpoint.
